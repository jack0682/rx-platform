# Provenance of Runtime restart restrictions

`Engine::open` adds a `runtimeinvalidationorigin` original in the same transaction that records RuntimeRestart restrictions for existing cells. The key binds the exact block ID, and the schema is `rx.runtime-invalidation-origin.v1`. Created records are read only at revision 1; existing originals are not modified, and provenance is not synthesized for historical restrictions.

`RuntimeInvalidationOrigin` stores installation/store generation, cell, the original Block snapshot, previous/current Runtime boots, and previous/current cell revisions/epochs/scope vectors/configuration digests. The configuration digest is the same canonical-source SHA-256 used by existing process-change configuration references. Recording checks that exactly one new restriction was created, previous restrictions remain intact, and revision/epoch/scope incremented once. If the startup transaction fails, restriction/origin/new boot/Fence records roll back together.

`runtime_invalidation::load(tx, block_id)` checks the historical original and schema/key/revision/structure. `read_for_cell(tx, installation, cell_id, block_id)` additionally compares installation identity/generation/original block snapshot and non-regressing revision/epoch/scope at the current storage cut. Missing provenance returns None. An origin from a previous boot is also readable while the same block remains. Current configuration may differ from the historical origin, so callers must separately check suitability of application before/after and verification plans. Original references use the `RX-RUNTIME-INVALIDATION-ORIGIN-v1` digest from `digest()`.

This records the fact that the Runtime created a restriction. An empty P ledger or the existence of an origin is not evidence of Host/native work, equipment, material or personnel state. Reading an original itself does not clear blocks, qualify or start Runs. Historical RuntimeRestart restrictions without provenance and other restrictions such as OperatorHold remain. There are no SDK/common-or-cell normative/UI changes at this stage.

The read API for explicit selection is `GET /api/v1/runtime-restrictions?cell=...`. It requires one of the current Engineer/Verifier/ReleaseManager roles and access to the requested cell; registered-terminal sessions apply the existing terminal-authority intersection. In one transaction it checks the current installation and cell, then returns only latched RuntimeRestart blocks in ID order. The response is `{cell, revision, epoch, configuration_digest, restrictions:[{block, origin, origin_digest}]}`; without an original, both origin fields remain null. A mismatched or corrupted current origin rejects the query rather than being treated as absent. Queries do not create or modify origins, ownership bindings, blocks or qualifications.

## Connection to requalification requests and final activation

`Requalification.Begin.runtime_restrictions` is an explicit map of block IDs and exact origin digests to review for clearance. It contains at most 128 entries, which must belong to the requested impacted cells. The origin's configuration digest must match the before or after configuration actually applied by that Change. Historical provenance is not fabricated from a reason name, and current restrictions are not selected wholesale.

New requests use v2 and include the original origin snapshot and complete impact digest. These are bound unchanged through request → report digest → signature. v1 records preserve existing serialization and digests. Begin atomically adds ownership records bound to Change/Job/request digest/origin digest but does not clear restrictions. Recording a restart restriction on the original active qualification's Change also preserves the origin digest from the same transaction.

Existing procedures remain required: reports across 6 verification areas, independent review, issuance, confirmation by every Host and final activation. `owned_clear` compares both the origin selected by the current Job and its immutable binding to that Job. Selection in J1 does not let J2 without a selection clear the restriction. Across failures before/after commit, the same request key retrieves the same result without leaving partial ownership records.

Impact checks recalculate the complete closed set of sharing relationships using all target cells' Hosts/resources as seeds. The target cell set and configuration/shared-impact digest are checked for both pending requests and active qualifications. Even if the original cell revision is unchanged, a new shared cell prevents using the old qualification as current.

Tests verify initial startup → process application → explicit selection → signed report → independent approval → Host confirmation → activation, as well as omitted/tampered selections, reuse by a different Job and changes in shared impact. They also check entry into a new Begin after P restarts from active state, but actual Host producer reconnection/reregistration and complete reactivation remain separate incomplete paths. Actual equipment or material state has not been verified.
